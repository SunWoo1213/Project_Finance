# AI 리포트 작성 파이프라인 진단

날짜: 2026-06-08
상태: 분석 및 문서화만 수행, 코드 변경 없음

## 목적

AI 리포트가 어떤 경로로 작성되고 저장되는지 현재 코드 기준으로 정리하고, 사용자가 보는 "리포트 작성 거부" 또는 `GET /api/reports/{ticker}` 404가 왜 반복되는지 원인을 분류한다.

중요한 결론: 사용자 화면과 챗봇은 리포트를 실시간 작성하지 않는다. 일반 사용자 요청은 저장된 scheduled `AIReport`만 조회한다. 신규 작성은 백엔드 스케줄러와 서비스 내부 gate를 통과한 경우에만 DB에 저장된다.

## 파이프라인 요약

1. 앱 시작 시 `backend/app/main.py`의 lifespan이 DB 준비, market warm-up, APScheduler 등록을 수행한다.
2. `ENABLE_SCHEDULER=true`이면 가격/뉴스 갱신 job이 등록된다.
3. `ENABLE_AI_REPORT_GENERATION=true`일 때만 리포트 job `generate_daily_reports`가 등록된다. 현재 구현은 interval job 하나에 `next_run_time=datetime.now() + REPORT_SCHEDULER_STARTUP_DELAY_SECONDS`를 지정해 기동 직후 1회 실행되도록 한다.
4. `generate_daily_reports()`는 `REPORT_SCHEDULER_TARGET_TICKERS`의 보수적 대상(`DGS10`, `XAU`, `BTC-USD`, `NVDA`, `005930.KS`)을 DB `Asset`으로 보장한 뒤 순회한다.
5. 회당 생성 개수는 `REPORT_SCHEDULER_MAX_REPORTS_PER_RUN`으로 제한되고, `REPORT_SCHEDULER_ASSET_COOLDOWN_HOURS` 안에 이미 저장된 리포트가 있으면 건너뛴다.
6. 각 ticker는 `generate_report_for_ticker()`로 넘어간다.
7. 서비스는 `market_cache["prices"]`에서 가격 payload를 찾고, 없으면 `ensure_price_cache_for_ticker()`로 ticker 단위 캐시 보강을 한 번 시도한다.
8. 가격 payload가 끝내 없으면 `ValueError`로 `provider_unavailable` 실패가 기록되고 저장하지 않는다.
9. 최신 컨텍스트와 뉴스가 병합되고, `_build_report_facts()`가 자산군별 필수 fact matrix를 만든다.
10. `_grade_report_readiness()`가 `ready`, `limited`, `blocked`를 결정한다.
11. `blocked`이면 LangGraph/LLM을 호출하지 않고 `ReportReadinessError`를 발생시킨다. DB에는 저장하지 않는다.
12. `ready` 또는 `limited`이면 LangGraph 파이프라인이 실행된다: financial/news/macro 수집, synthesis, bull/bear/risk 분리, research packet 구성, writer, format validator, numeric fact checker, qualitative claim checker, evaluator 순서다.
13. format/numeric/qualitative/evaluator gate 중 하나라도 실패하면 writer로 돌아가며, `REPORT_MAX_REVISIONS` 기본 7회에 도달하면 종료된다.
14. 최종 `is_pass=false`이면 `ReportQualityError`가 발생하고 저장하지 않는다. 단 format은 통과했고 numeric fact checker만 실패한 경우에는 미지원 숫자를 결정적으로 정제한 뒤 재검증을 통과할 때만 저장한다.
15. 통과한 결과만 `AIReport`로 저장되고 `GET /api/reports/{ticker}`가 200으로 반환할 수 있다.

## 사용자 조회 경로

`frontend/src/pages/AssetDetail.jsx`는 Plus/Pro 권한이 있는 사용자에게만 `GET /api/reports/{ticker}`를 호출한다. 이 요청은 저장된 최신 리포트만 읽는다.

저장된 행이 없으면 백엔드는 `404 No report found for ticker`를 반환하고, 프론트엔드는 `quality_status="scheduled_pending"`, `reason="scheduled_report_not_ready"` 상태를 보여준다. 프론트엔드는 더 이상 `POST /api/ai/generate/{ticker}`로 fallback 생성하지 않는다.

## 수동 작성 API가 거부되는 이유

`POST /api/ai/generate/{ticker}`는 현재 일반 사용자에게 항상 HTTP 403을 반환한다.

코드 위치:

- `backend/app/main.py`의 `ensure_report_generation_allowed()`
- `backend/app/main.py`의 `generate_report()`

응답 메시지는 "Manual AI report generation is disabled. Reports are generated by the backend scheduler."이다. 이는 오류라기보다 비용과 품질 통제를 위한 제품 정책이다. Plus/Pro 권한은 리포트 조회 권한이지 즉석 작성 권한이 아니다.

## 예약 작성이 저장을 거부하는 주요 조건

### 1. 운영 스위치로 생성 자체가 꺼진 경우

`ENABLE_AI_REPORT_GENERATION=false`이면:

- lifespan에서 `generate_daily_reports` job을 등록하지 않는다.
- `generate_daily_reports()`는 DB 세션이나 provider/LLM 호출 전에 return한다.
- `generate_report_for_ticker()`도 즉시 `RuntimeError`로 차단한다.

로그 신호:

- `AI report generation scheduler skipped because ENABLE_AI_REPORT_GENERATION=false`
- `AI report generation skipped because ENABLE_AI_REPORT_GENERATION=false`

이 경우 기존 저장 리포트 조회는 가능하지만 신규 작성은 없다.

### 2. 스케줄러가 발화하지 못한 경우

이전 배포 로그에서는 리포트 job 시작 로그가 없고 프로세스가 startup delay 전에 종료되어 `ai_reports`가 비어 있었다. 현재 코드는 interval job에 `next_run_time`을 부여해 이 문제를 완화했지만, 런타임이 `REPORT_SCHEDULER_STARTUP_DELAY_SECONDS`보다 빨리 종료되면 여전히 첫 발화를 놓칠 수 있다.

로그 신호:

- `Scheduler started`는 있으나 `AI 리포트 생성 시작` 또는 ticker별 `리포트 생성 시작`이 없다.
- `Shutting down`, `Finished server process`가 startup delay 전에 반복된다.

근본 안정화는 상시 가동 런타임 또는 외부 cron/task endpoint 같은 인프라 설계가 필요하다.

### 3. market/provider 데이터 부족으로 readiness가 `blocked`인 경우

`_grade_report_readiness()`는 다음 조건에서 저장 전 차단한다.

- `price.value`가 `None`, 빈 문자열, `0`인 경우
- fact matrix에서 `price`, `index_level`, `yield_level`, `spot_or_futures_price` 같은 primary fact가 `missing_required`인 경우
- `CRYPTO` 또는 `COMMODITY`에서 필수 fact가 3개 이상 빠진 경우

이 경우 `ReportReadinessError`가 발생하고 LLM을 호출하지 않는다. 즉 "리포트를 쓰다가 실패"가 아니라 "쓸 최소 데이터가 없어 쓰기 전에 멈춤"이다.

로그 신호:

- `report generation failed (failure_type=readiness_blocked, missing_required=..., blocking_reasons=...)`
- `가격 데이터가 없어 리포트 생성을 중단했습니다.`
- `Blocking facts are missing: ...`

대표 원인:

- Finnhub quote 장애 또는 provider timeout
- FMP 무료 플랜에서 quote/history가 `402 Payment Required`
- `ENABLE_STOOQ_FALLBACK=false`라 Stooq 보강 경로가 꺼져 있음
- CoinGecko/data.go.kr/FRED 등 대상별 필수 API key 누락 또는 응답 실패
- 직전 유효 stale snapshot이 없어 provider 실패를 대체할 값이 없음

### 4. LangGraph 품질 gate에서 탈락한 경우

readiness가 `ready` 또는 `limited`여도 작성된 초안이 gate를 통과해야 한다.

거부 지점:

- 필수 Markdown 섹션 누락
- 자산군별 framework section 누락
- writer가 fact matrix에 없는 숫자를 만들어냄
- 확인되지 않은 규제, ETF, 기관자금, 정책 변화, 실적, 공급, 온체인 주장
- evaluator가 배포 가능한 품질이 아니라고 판단
- 위 실패가 `REPORT_MAX_REVISIONS`까지 반복됨

로그 신호:

- `graph_node: report_format_validator_node fail`
- `graph_node: fact_checker_node fail`
- `graph_node: qualitative_claim_checker_node fail`
- `report generation failed (failure_type=quality_failed, revision_count=..., feedback=...)`

이 경우에도 DB에 저장하지 않으므로 조회 API는 계속 404다.

### 5. 이미 최근 리포트가 있어 스케줄러가 건너뛴 경우

같은 `Asset`에 대해 cooldown 범위 안에 `AIReport`가 있으면 새 리포트를 만들지 않는다.

로그 신호:

- `{ticker} 오늘 리포트 이미 존재 - 건너뜀`

이 경우는 실패가 아니며 기존 리포트 조회가 200이어야 정상이다.

## 왜 계속 "거부"처럼 보이는가

표면적으로는 사용자가 리포트를 요청할 때마다 403 또는 404를 보게 된다.

- 403은 수동 작성 API가 정책적으로 닫혀 있다는 뜻이다.
- 404는 저장된 `AIReport`가 없다는 뜻이다.
- 404가 발생해도 frontend/chatbot은 작성 fallback을 호출하지 않는다.
- 예약 job이 발화하지 않았거나, 발화해도 provider/readiness/quality gate에서 탈락하면 DB 행이 생기지 않는다.
- DB 행이 없으면 다음 조회도 다시 404가 되므로 "계속 거부"처럼 반복된다.

따라서 원인 판별은 HTTP 코드만 보면 안 되고, 배포 로그에서 아래 순서로 확인해야 한다.

1. `ENABLE_SCHEDULER`와 `ENABLE_AI_REPORT_GENERATION`이 모두 true인가.
2. `AI 리포트 생성 시작` 로그가 있는가.
3. ticker별 `{ticker} 리포트 생성 시작` 로그가 있는가.
4. 실패 로그가 `provider_unavailable`, `readiness_blocked`, `quality_failed` 중 무엇인가.
5. 성공 로그 `{ticker} 리포트 생성 완료` 이후 `GET /api/reports/{ticker}`가 200인가.

## 운영 확인 체크리스트

- 수동 생성이 필요한 상황인지, 아니면 저장 리포트 조회만 원하는 상황인지 먼저 구분한다.
- 사용자 화면에서 즉석 작성을 열려면 비용 증가와 제품 정책 변경이므로 사전 승인이 필요하다.
- 예약 생성을 원하면 `ENABLE_SCHEDULER=true`, `ENABLE_AI_REPORT_GENERATION=true`, `OPENAI_API_KEY` 및 대상 provider key가 준비되어야 한다.
- 무료 provider만 쓰는 환경에서는 `ENABLE_STOOQ_FALLBACK=true`와 `STOOQ_API_KEY`가 XAU, US index, US stock history 보강에 중요하다.
- NVDA 같은 STOCK_US는 현재 Finnhub quote 실패 시 FMP quote/history 및 Stooq history로 보강을 시도하지만, 모든 provider가 동시에 실패하면 price 0으로 readiness blocked가 될 수 있다.
- 품질 실패가 반복되면 `feedback`, `unsupported numbers`, `missing framework sections`를 기준으로 writer prompt 또는 fact source를 조정해야 한다. 단 리비전 한도를 올리면 LLM 비용이 증가한다.

## 검증

이번 작업은 분석 및 문서화 작업이므로 LLM 호출, scheduler 실행, backend/frontend 테스트는 수행하지 않았다. 코드 변경도 없으므로 build/lint는 생략했다.

정적 확인:

- `rg`와 `Get-Content`로 위 관련 파일의 현재 구현을 확인했다.
- `.env` 또는 secret 값은 열람하지 않았다.

## 후속 위험

- 운영 환경에서 `ENABLE_AI_REPORT_GENERATION=true`를 켜면 OpenAI와 market provider 비용이 발생한다.
- 스케줄러 cadence, target ticker 확대, manual generation 개방은 비용과 정책 변경이므로 사용자 확인 후 진행해야 한다.
- 인프라가 startup delay보다 짧게 재시작되면 코드 보정 후에도 예약 job이 저장 리포트를 만들기 어렵다.
- provider 무료 플랜 제약이 해소되지 않으면 readiness blocked 또는 quality failed가 반복될 수 있다.
